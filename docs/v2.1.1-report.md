# V2.1.1 · 公网 Cookie 安全策略

Mac Cloudflare Tunnel 经 NAS 的 Docker Bridge 发布端口访问夜曲时，普通内网请求与 Tunnel 请求可能具有相同的网关对端。不能为获得 Secure Cookie 而信任这个共享网关。

新增可选环境变量 `NOCTURNE_SECURE_COOKIE_HOSTS=jingbo.men`。请求 Host 准确匹配时，会话和设备 Cookie 强制添加 Secure，保留 HttpOnly、SameSite=Lax、host-only 范围；清除 Cookie 同样使用该策略。默认空值保持旧行为，内网 IP 的 HTTP 登录不受影响。错误域名配置启动失败，不写入数据。

Host 只参与增加 Cookie 限制。clientInfo / isHttps、客户端 IP、代理信任、登录限流和 LAN 豁免逻辑均未修改；X-Forwarded-Host 不参与匹配。此方案不验证实际传输协议，也不替代 Cloudflare Access、HTTPS 入口或源站隔离。共享网关模式下 client.https=false 仍是预期结果。

数据、账户事务、Cookie 名称、UI、空间及备份恢复格式不变。public 与 V2.1.0 完全相同，已有 V2.1.0 资源基线覆盖本次静态资源。

## 验证

新增 8 项安全测试，覆盖初始化、登录、设备登记、退出清除、内网 HTTP、域名匹配与伪造头、可信 HTTPS 兼容、共享对端限流和错误配置启动保护。安全专项 18/18；V2.1.0 实现上的两个公网 Secure 回归测试均失败，修复后通过。

完整自动化测试与双架构发布结果在发布完成后登记。只使用现有 Docker Actions 的新 SHA 镜像标签，不创建版本 Git tag，不修改 main、旧镜像、NAS 或 Cloudflare。

## 部署后验收

保留 Bridge 网络，增加上述环境变量；不添加共享网关 TRUSTED_PROXY_CIDRS。代理必须保留 jingbo.men 的 Host。仅在公网 HTTPS 入口完成新登录，在浏览器 Cookie 表检查 nocturne_sid 与 nocturne_dev 的 Secure、HttpOnly、SameSite=Lax；通过内网 IP 的 HTTP 登录应仍正常。公网域名的 HTTP 登录不受支持，因为浏览器不会正常使用其 Secure Cookie。

回滚使用上一固定 V2.1.0 镜像并移除该环境变量，不需迁移数据；回滚不包含本次 Cookie 修复。实际 NAS 升级与域名切换由用户另行执行。
