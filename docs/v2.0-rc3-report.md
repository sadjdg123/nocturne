## 2. 「RC.2 报告在远端缺失」的原因

- RC.2 的推送分两批：04:15 一批（代码 + README + 升级手册等，最后一个文件 `server.js` 触发 CI → 远端提交 `3d5beaf`，镜像 `sha-3d5beaf`）；
  04:24 第二批（`docs/v2.0-rc2-report.md` + `tools/v2test` / `test/v2test-kit` 的 RC.2 镜像固定），远端提交 `fa987e1…09cb30e`，都被 `paths-ignore` / `[skip ci]` 跳过构建。
- 外部评审看的是**镜像对应的提交 `3d5beaf`**（也是当时的分支头）：那棵树里确实没有 `docs/v2.0-rc2-report.md`（用 `git/trees/3d5beaf…?recursive=1` 复核：121 个文件，缺这一份，另有 4 个 v2test 套件文件是旧版本）。
- 上一轮的「远端树一致」是在第二批之后对**分支最新提交**做的比对，而旧版 `gh_v2.py verify` 只打印一个计数，不说明比对的是哪个远端提交，也不检查工作区、不能要求指定文件存在、出错也返回 0——于是「分支头一致」被当成了「镜像提交一致」。
  报告里写的 `3d5beaf`（镜像）与文档实际所在的 `09cb30e` 不是同一个提交。
- 修正：`gh_v2.py verify <ref> [--require 路径,…]` 改为先把 ref 解析成提交 SHA 并打印、用递归 git tree（截断即失败）逐文件比对 blob SHA、工作区不干净即失败、可要求指定路径存在、不一致时退出码 1；另加 `gh_v2.py diff` 列出待上传文件。
  RC.3 的推送顺序改为**文档在前、代码在后**：触发 CI 的那一个提交已经包含全部文档；之后只追加本报告的镜像信息（仅文档提交）。

## 3. 修复

### P-2 旁路必须是 fmt:2 + 合法 h（提交见第 5 节）

- RC.2 的漏洞：`guardMatches()` 在 `h` 缺失时跳过指纹校验、不看 `fmt`。RC.1 写的旁路正是旧格式（没有 `fmt` / `h`），而 RC.1 写的 `hist` 条目又没有 `g:2`，
  于是「RC.1 旁路写入失败（RC.1 静默）→ 之后删光 / 修改空间 → 回滚 V1.1 丢掉空间 → 直接升级」会把**删掉的空间找回来**（复现测试在 RC.2 代码上失败 4 / 4）。
- 修复：新增 `guardFormatOk`——`fmt === 2`、`h` 为 64 位小写十六进制、`version` 为整数、`spaces` 为数组或 `null`；`guardMatches` 先查格式，再要求 `h` 与 `hist` 中该版本的指纹**严格相等**。
  旧格式 / `fmt` 不对 / `h` 不合法的旁路**永不用于自动找回**（日志 `spaces guard: stale <账户> guard v<N> has an old or invalid format (fmt/h)`，管理员诊断 `kind: "stale"`）。
- 后备（快照环里最后一个 `g:2` 版本）多一道检查：RC.1 旧格式旁路的版本比这个 `g:2` 版本还新（= RC.1 在那之后又写过），快照环里那份已经过期 → 不找回
  （日志 `spaces guard: skipped … old-format guard vN is newer than the last V2 version vM`）。宁可不找回，用户可在「恢复较早的版本」手动恢复。
- 启动自愈：配置最后是 V2（含 RC.1）写的 → 旁路缺失 / 损坏 / 旧格式（`old format`）/ 格式不对（`invalid format`）/ 版本或指纹不符 → 按当前配置重写，只写旁路、不改配置（逐字节核对）。
  所以正常的 RC.1 → RC.3 升级第一次启动就把旧格式旁路换成 `fmt:2`，不受影响。

### P-3 atomicWrite 撞名时不删别人的文件

- RC.2：`open(tmp, "wx")` 因重名失败（`EEXIST`）时，`finally` 仍执行「删除临时文件」——删掉的是那个**已存在的、不属于本次写入**的文件。
- 修复：`created` 标记只在 `open` 成功后置位（同时登记 `ownTmps`）；清理只在 `created && !done` 时进行。`EEXIST` 原样抛出，目标文件不动。导出 `atomicWrite` 供单元测试。

### 管理员提示（旁路写入失败）

- RC.2 前端**没有**处理保存响应里的 `guardWarning`，也没有读 `/api/health` 的 `guard`（只有接口字段，没有任何界面）。
- RC.3：
  - 保存响应带 `guardWarning` 且当前账户是管理员 → 读一次 `/api/health`，用已有 toast 提示：
    「空间保护记录未能保存（账户 X）：配置本身已保存，但回滚到旧版本后自动找回空间的保护暂时失效。请检查 NAS 磁盘空间和 data 目录的写入权限，并尽快做一次备份。」
  - 管理员打开页面时也查一次 `/api/health`（另一台设备 / 刷新后也能看到）。
  - 每次「发生」只提示一次：服务器诊断新增 `since`（这一轮连续失败开始的时间，同一轮内不变），前端以「账户 + since」为键记在本机 localStorage；修好后再失败 = 新的一次，会再提示。
  - 设置 → 账户 → 管理员「连接诊断」行追加「空间保护异常：<账户>（记录未能保存：<错误码>，请检查磁盘空间 / 权限并备份）」或「（记录已过期，不会用于自动找回）」。
  - 普通账户不提示。

## 8. 兼容与风险

- RC.1 → RC.3：RC.1 的 data 原样可用（会话、配置、空间、图标、壁纸、第二账户）；首次启动把 RC.1 旧格式旁路重写为 `fmt:2`（只写旁路）。RC.3 → RC.1 回滚照常读写（`test/rc1-compat.test.js`）。
- 行为变化：`RC.1 → V1.1 → 直接升 RC.3` 不再自动找回空间（以前会用 RC.1 旧格式旁路，可能复活已删除的空间）；需手动「恢复较早的版本」。
- 管理员诊断在内存里，容器重启后清空（启动自愈会重写旁路；仍写不进去会再次记录并提示）。
- 真机 Safari / 真实 HTTPS / 群晖实机的人工验收仍按 `docs/v2.0-manual-acceptance.md` 待做。
