## 1. 数据模型

唯一的项目来源仍是 `data.groups[].items[]`。空间**只存空间信息、引用、顺序和空间自己的显示配置**，从不复制项目：

```jsonc
// 同步的账户配置（/api/config 的 data）里新增的可选字段
"spaces": [
  { "id": "s-nas", "name": "NAS", "groupIds": ["st0rage9kq2"], "itemIds": ["e7h2kq9b1m"], "theme": "frost", "density": "compact" }
]
```

| 字段 | 类型 / 限制 | 含义 |
| --- | --- | --- |
| `id` | 字符串，`/^[A-Za-z0-9_-]{1,40}$/`，不能是 `all`，配置内唯一；创建后不变 | 稳定 ID（本机「当前空间」只记它） |
| `name` | 字符串，修剪后 1–24 个字符（按 Unicode 码点），无控制字符；不区分大小写不重名，不能叫「全部」 | 显示名称 |
| `groupIds` | 必填，字符串数组 ≤500，每个 ≤64 字符 | **主关系**：整组引用（组内现在和以后的项目都在这个空间） |
| `itemIds` | 可选，同上 | 单个项目引用：项目不必带上整组也能出现在空间里 |
| `theme` | 可选，`default` / `dawn` / `dusk` / `frost` | 空间色调（对应预览里的 全部 / 日常 / 娱乐 / NAS） |
| `density` | 可选，`comfortable` / `poster` / `compact` | 空间内容密度 |
| 其他键 | **拒绝**（400） | 防止把项目实体塞进空间 |

- 空间上限 24 个（不含「全部」）。
- **「全部」** 是虚拟空间（id `all`）：不存进 `spaces`、不能删除，永远是全部分组 + 全部项目的完整集合。
- 没有 `spaces` 字段 = 只有「全部」。模型从不主动给配置加这个字段；`spaces: []` 表示用户明确删光了自定义空间。
- 代码：`public/spaces.js`（UMD，前端 `window.NocturneSpaces`，服务端 `require`，零依赖）。

### 顺序定义

- 空间顺序 = `spaces` 数组顺序（`move()` 调整）。
- **空间内的分组和项目一律按全局顺序显示**：分组按 `data.groups` 顺序，组内项目按该组 `items` 顺序。`groupIds` / `itemIds` 只是集合，其中的先后不影响显示。全局拖动排序后，所有空间同时跟着变——不存在「每个空间一套顺序」。
- 只因 `itemIds` 出现的项目，显示在它**当前所在分组**的标题下，该分组只显示被引用的那几个（`view()` 返回 `whole:false`）。

### 引用规则

| 操作 | 结果 |
| --- | --- |
| 编辑项目（url / lan / wan / icon / aliases / 标题…） | 同一实体，所有空间同时生效 |
| 删除项目 | 从所有空间的 `itemIds` 里删掉 |
| 删除分组 | 从所有 `groupIds` 删掉；组内项目随组删除，它们在 `itemIds` 里的引用也删掉 |
| 在分组间移动项目 | id 不变，`itemIds` 引用继续有效（跟着项目走）；整组引用的空间则按「新组在不在这个空间」决定是否显示 |
| 复制项目 | 新 id，**不会**自动加进任何 `itemIds`；若所在分组整组在空间里，则随分组出现 |
| 删除空间 | 只删这条空间记录；分组、项目、上传图标、壁纸都不动 |
| 撤销 | 空间与分组 / 项目在同一次 `commit` 里改，一起撤销 |

悬空引用由 `prune()` 清理，触发点：前端每次 `commit` 之后、读本机缓存时（`load`）、读服务器配置时（`adopt → normalize`）、JSON 导入后；服务端每次保存前（见 §3）。空空间保留（阶段 2 显示空状态和「管理空间」入口）。

## 2. 本机「当前空间」

- 存在 `localStorage["nocturne.space:<账户名小写>"]`（纯静态页：`nocturne.space:~local`）。值为空间 id；选「全部」时删除该键。
- **不在 `A.state` 里**，所以不进 `snapshot()`、不进本机配置缓存 `yeqv.v1`、不产生服务器版本、不会触发 409。
- 每个账户一个键：换账户读不到上一个账户的选择；上一个账户的配置缓存本来就会在换账户时被清掉（V1.1 boot 逻辑），所以也看不到它的空间定义。
- 记住的 id 不存在（被删、别的账户的、乱写的）→ 回落「全部」。
- 阶段 1 只有程序接口 `App.spaces`（`list / view / selected / select / selKey / model`），没有界面。

## 3. 同步 / 服务端

空间定义走现有的一套：`snapshot()/adopt()/load()`、`/api/config` 版本号、409 冲突面板、opId 去重、撤销、备份环与「恢复较早的版本」、JSON 导入导出。没有新增同步引擎、`A.url` 或 URL 校验器。

服务端 `server.js`：
- `PUT /api/config` 和 `POST /api/config/stash`：`spacesError()` 用 `SPACES.check()` 校验结构，不合法 → **400 `{code:"bad_spaces", spaces:[{where, problem}]}`**（与 V1.1 的 `bad_aliases` 同一风格），不写入。URL 白名单、aliases 限制、权限、403/409/422 逻辑不变。
- 保存前 `reconcileSpaces()`（在用户锁内）：
  1. **旧版前端保护**：请求体没有 `caps:["spaces"]` 且 `data` 里没有 `spaces`，而服务器当前版本有 `spaces` 字段（**包括 `[]`**）→ 沿用服务器上的空间定义（返回 `spacesKept:true`）。V2 前端每次推送都带 `caps`，所以它明确删光空间 / 恢复默认不会被「保护」回来。
  2. **悬空引用规则**：`groupIds/itemIds` 里指向不存在的分组 / 项目的 id 删掉（返回 `spacesPruned:n`）。
  有改动时同时返回 `migrated:true`，V1.1 与 V2 前端都会据此重新拉取。内容指纹 / opId 仍按收到的原始内容计算，不影响去重。
- 备份列表、409 响应带 `spaces` 个数（供冲突面板 / 恢复列表显示）：没有字段 → `null`，`[]` → `0`。
- `GET /api/config` 不为空间改写数据、不升版本。

前端 `public/nocturne.js` / `index.html`：推送体带 `caps`；`normalize()` 清洗空间；JSON 导入先 `check(data, {lenient:true})`（结构不合法 → 报错不导入；重名、悬空引用 → 清洗后导入）；恢复一个**没有 `spaces` 字段**的旧备份时保留现有空间（随后按恢复后的分组清引用）。

### 真实数据（给阶段 2/3）

- `/api/status` 已有服务端实测延迟：`ms` = `process.hrtime` 量出的首个响应耗时（整数毫秒），探测失败 / 未探测 / 只靠容器状态时为 `null`，另有 `checkedAt`。新增测试锁定这一点（`spaces-server.test.js` 最后一项）。界面应在 `ms == null` 或没有结果时显示「未检测 / 未知」。
- `recent`（最近使用）只存项目 id 和先后，**没有时间戳**。预览里的「x 分钟前」在正式版没有数据来源；阶段 2 若要显示时间需另加本机字段，否则只显示顺序。
- 生产代码中没有任何模拟值。

## 4. 回滚 / 旧版兼容矩阵（实测）

旧版 = 按 blob SHA 取出的 V1.1 `server.js + package.json + public/{index.html,nocturne.js,urlcheck.js,netmode.js,cmdrank.js,Sortable.min.js}`（`test/v11.js`），由 `helpers.startServer({root})` 真起进程；前端用 jsdom 真实运行旧版页面脚本（`test/browser.js`，阻断对外网络）。测试文件 `test/rollback-compat.test.js`。

| 场景 | 实测结果 |
| --- | --- |
| (a) 旧服务端收到带 `spaces` 的配置 | 200，原样存储、原样返回（字节相同）；备份环原样保存（旧版备份列表不显示空间数）。**旧服务端不校验 spaces**：`spaces:"garbage"` 也 200。旧服务端上，不带 spaces 的强制覆盖会让当前版本丢掉空间（备份里仍在）。 |
| (b1) 旧前端 + 旧服务端：读新配置后编辑项目 | 旧前端把未知顶层字段留在 state 里，推送时原样带回 → **空间保留**。 |
| (b2) 旧前端删掉被引用的分组 | 空间保留，但留下**悬空引用**（旧版不清理）；升级回 V2 后被清掉，见 (d)。 |
| (b3) 旧前端 导出 / 导入 | 导出 JSON 含 `spaces`；导入 V2 导出的文件 → 空间保留（`Object.assign`）。 |
| (b4) 旧前端「恢复默认」 | 空间随全部配置一起被清空（用户明确的全量重置；会先自动导出）。 |
| (b5) 旧设备有 V2 之前的离线修改（缓存无 spaces、dirty），用户在冲突面板选「用本机版覆盖」 | **旧服务端：当前版本丢失空间定义**（被覆盖前的版本进备份环，可在「恢复较早的版本」找回）。**V2 服务端：空间保留**（`spacesKept`）。 |
| (b6) 升级时还开着的旧前端页面 → V2 服务端 | 编辑：空间保留；删被引用的分组：服务端清悬空引用并回 `migrated`，旧页面重新拉取后拿到干净副本。 |
| (c) V2 写的带空间备份，回滚到 V1.1 后在旧前端里「恢复较早的版本」 | 旧服务端能列出、读取 V2 写的备份环；通过旧前端真实 UI 恢复后，空间定义**原样恢复**。 |
| (d) 回滚期间 V1.1 写的数据再升级回 V2 | 新服务端 GET 原样返回、不改写不升版本；V2 前端载入时清掉悬空引用、不报错、不推送；下一次真实修改时存入干净引用。回滚前 V2 记下的 opId 在 V2→V1.1→V2 之后仍能识别重复推送（V1.1 保留了 `ops`），同 opId 不同内容仍 422。 |

### 纯回滚到 `sha-3e6da3c` 的残留风险

1. **V1.1 服务端没有旧版保护**：回滚期间若某台设备用不含 `spaces` 的数据覆盖（b5 的情形，或任何不带 spaces 的保存），当前版本的空间定义会丢失；只能从「恢复较早的版本」找回（备份环默认 30 份 / 20MB，过旧的会被挤掉）。
2. V1.1 不校验 `spaces`：回滚期间无法阻止畸形空间数据写入；升级回 V2 后前端会清洗（`normalize`），但服务端对已存储的畸形结构只在下次保存时拒绝（400）——此时前端已清洗过，正常不会触发。
3. V1.1 删分组 / 删项目不清引用（b2）；V2 读到后自动清理，不影响使用。
4. 回滚**不需要删除 `data/`**：V1.1 能读 V2 写的配置、备份、ops/hist（测试全部在同一个 data 目录上切换版本完成）。

## 7. 复查修正

### A. 前端处理 400 `bad_spaces`（`public/nocturne.js`）

- 以前：`bad_spaces` 落到通用错误分支 → 提示「暂时无法同步」并每 15 秒重推同一份内容；切后台（keepalive）、`pagehide`、`online`、每次渲染也都会再推。
- 现在：提示「空间设置格式有误，服务器未保存。本机修改已保留，改动后会再同步」（带「重试」按钮）；**本机修改、本机缓存和脏标记全部保留，什么都不回退**；被拒的那份内容（`snapshot` 字符串）记在内存里，防抖推送、15 秒重试、切后台 keepalive、`pagehide`、`online` 对它一律跳过；内容再变（用户又改了）或点「重试」才重新推送。重新打开页面会补推一次（被拒标记只在内存里，单次不构成反复请求）。
- 其他路径不变：`bad_aliases`、不安全地址（`invalid`）、409 冲突、422 `opid_mismatch`、401、413、网络错误照旧。
- 测试 `test/spaces-badspaces-frontend.test.js`（3 个，jsdom + 真实服务端）：toast 文案与「重试」按钮、本机状态 / 缓存 / 脏标记保留、服务器版本不变；`openPage({timeScale:100})` 把页面里 ≥1 秒的定时器按比例缩短，约 5 分钟页面时间 + 所有推送入口反复触发 → 仍只有 1 次 PUT；「重试」恰好再推 1 次；新的修改恢复推送；修好后 200、脏标记清除；`bad_aliases` 文案和 409 冲突面板不受影响。修正前两个用例失败（已核对）。
- `nocturne.js?v=5`（后续 C 改为 `v=6`）。

### B. 区分「没有 `spaces` 字段」与 `spaces: []`（`server.js`）

- 以前：旧版前端保护只在服务器上的空间**非空**时生效 → 用户明确删光空间（`[]`）后，旧版前端一次保存就把字段变成「不存在」。
- 现在：只要服务器当前版本有 `spaces` 数组（含 `[]`）就沿用；没有字段的账户保存后仍然没有字段（不凭空加）。备份列表 / 409 的空间数：没有字段 `null`、`[]` 为 `0`（原来两者都是 `0`）。备份文件本来就原样存 `data`，`[]` 与缺失照原样保留。
- 前端已正确区分（`normalize` 遇到 `[]` 保持 `[]`、`bkRestore` 只在备份**没有字段**时沿用当前空间），新增测试锁定。
- 测试 `test/spaces-empty.test.js`（3 个）：新前端存 `[]` → 旧前端保存 → 文件与 GET 仍为 `[]`、同内容不升版本；从没有空间的账户经旧前端 / 新前端保存仍无字段；备份环文件、`?backup=`、备份列表（`null` / `0`）、409（`0` / `null`）；V2 恢复 `[]` 备份 → `[]`；旧前端恢复无字段备份 → 保留 `[]`；jsdom：载入 `[]` 不推送、编辑后推送带 `[]`、通过真实 UI「恢复较早的版本」把一个空间恢复成 `[]`、重载后仍是 `[]`。修正前两个服务端用例失败。`spaces-frontend.test.js` 中对 V1.1 备份的断言随之由 `spaces === 0` 改为 `=== null`。

### C. 原型安全的 id 字典（`public/spaces.js`、`server.js`）

- `ID_RE`（`/^[A-Za-z0-9_-]{1,40}$/`）允许 `constructor`、`toString`、`__proto__`、`hasOwnProperty`、`valueOf`、`prototype`；引用只要求 ≤64 字符的字符串；分组 / 项目 id 不受限制。所以模型必须扛得住这些名字。
- 修正前的实际问题：空间 id `constructor` 被判「id 重复」；名称 `constructor` 被判重名；未知字段 `constructor` / `__proto__` 通过了 `KEYS` 白名单；指向 `toString` 等不存在分组的悬空引用被当成存在、清不掉；分组 id `__proto__` 会改掉索引对象的原型；`membership()` 遇到分组 id `constructor` 直接抛错；服务端 `/api/status` 按项目 id 建表，项目 id `__proto__` 的状态被吞掉。
- 现在：`spaces.js` 所有 id 字典用 `Object.create(null)`，判断一律用自有属性（`hasOwnProperty.call`），`KEYS` 也是无原型集合，`setLook` 只认自有键，`membership()` 返回无原型对象；`statusFor()` 用无原型对象，前端 `A.statusFor` 只认自有属性。`spaces.js?v=2`、`nocturne.js?v=6`。

### 记录的决定

1. **回滚限制**：开发期间，用户接受 §4「纯回滚到 `sha-3e6da3c` 的残留风险」所述的 V1.1 回滚限制。但**在 V2 部署到生产（NAS）之前，必须先设计好安全的生产回滚流程**，不能只靠会轮换的备份环（默认 30 份 / 20MB，旧版本会被挤掉）。方向：首次以 V2 启动前，把每个账户的当前配置导出成一份**固定的升级前快照**（例如 `data/pre-v2-snapshot/<账户>-<时间>.json`，带版本号与内容指纹），这份快照永不参与轮换、不被自动清理；回滚说明写明「回滚到 V1.1 → 如空间丢失，从固定快照或备份环找回」的具体步骤，并在部署前实测一次。
2. **阶段 2/3 向前兼容**：较旧的 V2 客户端不得悄悄丢掉较新版本加的空间字段。计划：前端 `normalize()` 原样保留不认识的空间键（不再删除），只清洗它认识的字段；服务端从「严格拒绝未知键」改为白名单 + 版本策略——给 `data` 加 `spacesVersion`（空间 schema 版本），服务端按版本决定允许的键集合，低版本客户端推送时服务端保留它不认识的已存字段（类似 `caps` 的旧版前端保护）；在此之前，阶段 1 服务端会对带新字段的配置回 400，而 A 的处理保证前端不会因此反复重推、也不会丢本机修改。
