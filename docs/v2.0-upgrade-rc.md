# 夜曲 Nocturne · V2 RC 升级与回滚手册（群晖 Container Manager）

> **认证事务修复版的优先规则：** 先阅读 [工程回滚与恢复边界](engineering-rollback.md)。强杀留下的认证事务必须先由修复版恢复；不能直接让 RC.1–RC.4 接管半完成状态。NAS 操作由用户自行执行，以下旧 RC 命令仅为历史示例。
> **先确认用哪份文档：**
>
> | 你现在 NAS 上跑的是 | 用哪份 |
> |---------------------|--------|
> | **V2 RC.1**（`sha-2ee0983`，`/api/health` 显示 `2.0.0-rc.1`）→ 想升到 RC.2 / RC.3 | **本文** |
> | 全新安装（NAS 上还没有夜曲的 `data/`） | **本文第 6 节** |
> | V1.1（`sha-3e6da3c`，`/api/health` 显示 `1.1.x`）→ 第一次升 V2，或 V2 回滚到 V1.1 | `docs/v2.0-upgrade-rollback.md` |
>
> 本文只讲 RC 之间的升级 / 回滚（数据已经是 V2 格式）。V1.1 ↔ V2 的固定快照、回滚写保护找回等内容在旧手册里。

> RC.5 可靠性修复已发布，固定镜像及测试见 `v2.0-rc5-report.md`。使用事务修复版后，强杀留下的 `.auth-transaction` 必须先由修复版恢复，再回滚 RC.1–RC.4；旧版不理解恢复侧车。详见 [账户事务与回滚边界](auth-transactions.md)。不要据本文的旧 RC 操作示例推断已获部署或发布授权。

## 0. 镜像（一律用 `标签@digest`）

当前候选、历史镜像、版本号及发布报告统一见 [开发交接版本表](HANDOFF-CODEX.md#01-版本--镜像--digest)。

**当前候选升级**：先按 `stopped-backup.md` 停写并保存、校验完整备份，再由用户自行使用版本表中的固定镜像，健康版本应与表中目标一致。回滚旧 RC 前先让认证事务修复版完成恢复并正常停止，见 `engineering-rollback.md`。下文旧 RC 命令作为历史示例，镜像与版本号按实际目标替换。

**RC.4 历史更新（RC.1 → RC.4）**：RC.4 = RC.3 + `nocturne.js` 缓存刷新修复（`?v=9`，升级后浏览器马上用新脚本，不会再用旧缓存跑最多一天），服务端和数据格式与 RC.3 相同（见 `docs/v2.0-rc4-report.md`）。
下文的步骤以 RC.3 为例写成，升 RC.4 时**把镜像换成版本表 RC.4 那一行**，期望版本号换成 `2.0.0-rc.4`，其余完全相同（日志里的 healed 等行为也一样）。

RC.3 = RC.2 + 旁路格式校验 / 临时文件撞名 / 管理员提示三处修复，见 `docs/v2.0-rc3-report.md`。要升 RC.2 时把镜像换成版本表 RC.2 那一行即可，步骤相同。

docker 同时写标签和 digest 时**以 digest 为准**；标签可能被重新指向，digest 不会。

下文假设（与 `tools/v2test` 套件默认值一致，按你的实际情况替换）：项目目录 `/volume1/docker/nocturne`（里面有 `docker-compose.yml` 和 `data/`），
容器名 `nocturne`，端口 `8088`，备份目录 `/volume1/backup/nocturne`，夜曲仓库的 `tools/` 已复制到 `/volume1/docker/nocturne/tools`。
命令都在群晖 SSH 里执行，需要 `sudo`。

**健康检查地址：生产端口绑定在 `192.168.50.141:8088`**（compose 里 `ports` 写的是 `"192.168.50.141:8088:8080"` 这种带 IP 的形式），
所以在 NAS 上用 `127.0.0.1:8088` / `localhost:8088` 是连不上的（`Connection refused`），**不代表容器坏了**。下文统一用变量 `NAS_IP`：

```sh
NAS_IP=${NAS_IP:-192.168.50.141}          # 默认生产绑定地址；以 docker port 的输出为准
sudo docker port nocturne 8080/tcp        # 例：8080/tcp -> 192.168.50.141:8088，箭头右边冒号前就是 NAS_IP
curl -s "http://$NAS_IP:8088/api/health"
```

换了网卡 / IP 或 compose 的 `ports` 改过时，按 `docker port nocturne` 的输出改 `NAS_IP`（输出是 `0.0.0.0:8088` 时表示绑定所有地址，用 NAS 的内网 IP 即可）。

## 1. 升级前：停写完整备份，然后校验

升级、回滚和灾备基准必须先确认并停止唯一写入实例；热备份的变化检测不等于跨文件事务快照。完整流程见 [停写备份](stopped-backup.md)，异常恢复见 [恢复材料保护](restore-recovery.md)。以下为操作者执行示例，本轮开发未操作 NAS：

```sh
cd /volume1/docker/nocturne
sudo docker stop nocturne
sudo docker inspect --format '{{.State.Running}}' nocturne   # 必须 false；确认唯一写入实例已停止
sudo sh tools/backup.sh -o /volume1/backup/nocturne ./data
sh tools/verify-backup.sh /volume1/backup/nocturne/nocturne-backup-<时间>.tar.gz
```

- 看到「备份完好：N 个文件 sha256 全部一致」再继续。归档含密码哈希和会话，权限 600，只放在你自己能读的位置。
- 当前保持停止，隔离恢复核验后再按批准的升级步骤继续；不要自动重新启动旧实例。
- 日常尽力备份可用热备份；短暂停机备份可用 --stop，但它只恢复原先运行的容器，原先已停止的实例不会自动启动。
- 记下归档文件名：回滚到「升级前的确切状态」时要用它（第 5 节）。

## 2. 升级前：查 RC.1 日志里的旁路写入失败

RC.1 写「回滚写保护旁路」（`data/spaces-guard/<账户>.json`）失败时**只记一行日志、不提示**（RC.2 起才会报错 / 提示）。先确认有没有发生过：

```sh
sudo docker logs nocturne 2>&1 | grep -n "spaces guard write"
```

（也可以在 Container Manager → 容器 → `nocturne` → 日志 里搜 `spaces guard write`。`docker logs` 只包含这个容器创建以来的日志。）

- **没有输出**：正常，继续第 3 步。
- **有输出**（例如 `spaces guard write admin ENOSPC …`）：说明当时磁盘满或权限不对。先处理再升级：
  - `df -h /volume1` 看剩余空间；`sudo ls -ln /volume1/docker/nocturne/data/spaces-guard` 看属主（应为 compose 里 `PUID`/`PGID`，常见 1026:100）。
  - 处理好以后照常升级。RC.3 启动时会按**当前配置**重写所有旁路（日志 `spaces guard: healed <账户> v<版本> (old format)`），只写旁路、不改配置。
  - 这条日志只影响「以后回滚到 V1.1 再升级时能不能自动找回空间」，不影响现在的配置内容。

## 3. 升级：改 compose 的镜像、重建容器

1. Container Manager → 项目 → `nocturne` → **停止**。
2. 项目 → **编辑**（YAML），把 `image:` 这一行改成 RC.3 的 `标签@digest`（**先把原来那一行复制下来**，回滚要用）：
   ```yaml
   image: ghcr.io/sadjdg123/nocturne:sha-e4de70b@sha256:e37da36ff107dac5df6f6af17c624f06d3ec5a2478b40be6703f80fe75e8d47b
   ```
   其余（`ports`、`volumes: ./data:/data`、`PUID`/`PGID`、`TRUSTED_PROXY_CIDRS` 等）不要动。
3. **构建 / 启动**（Container Manager 会按 digest 拉取并重建容器）。或 SSH：
   ```sh
   cd /volume1/docker/nocturne && sudo docker compose pull && sudo docker compose up -d
   ```
   包是私有的、拉取报 401 时：`sudo docker login ghcr.io -u <GitHub 用户名>`（令牌只需 `read:packages`），拉完可 `sudo docker logout ghcr.io`。

## 4. 升级后检查

```sh
sudo docker inspect --format '{{.Config.Image}}' nocturne        # 应是上面的 标签@digest
NAS_IP=${NAS_IP:-192.168.50.141}; sudo docker port nocturne 8080/tcp   # 核对绑定地址（见文首「健康检查地址」）
curl -s "http://$NAS_IP:8088/api/health"                        # "ok":true,"version":"2.0.0-rc.3"
sudo docker logs nocturne 2>&1 | grep -E "已启动|spaces guard|ERROR"
```

- 日志：`夜曲 Nocturne v2.0.0-rc.3 已启动 … cookies=nocturne_sid/nocturne_dev`；第一次以 RC.2 / RC.3 启动时每个账户一行
  `spaces guard: healed <账户> v<版本> (old format)`（RC.1 写的旁路是旧格式，按当前配置重写——**预期如此**）。不应出现 `ERROR`。
- 浏览器（不用重新登录：cookie 名默认不变，RC.1 的会话继续有效）：
  - 分组 / 项目 / 图标 / 壁纸 / 状态点与升级前一致；
  - **空间**：左侧（手机为底栏）的空间列表、每个空间里的分组 / 项目与升级前一致，切换正常；「管理空间」能打开；
  - 第二个账户也登录看一眼；管理员：设置 → 账户 → 连接诊断正常，没有「空间保护异常」字样；
  - 设置 → 账户 →「恢复较早的版本」列表能打开。
- 页面右下角若出现「空间保护记录未能保存…」提示（只给管理员）：说明 data 目录写不进去，按提示检查磁盘空间 / 权限、做一次备份，修好后重启容器即可。

**升级不会改动配置文件**：启动只重写 `spaces-guard/` 旁路。之后第一次保存配置时，配置里会出现 RC.2 起的新标记（见第 5 节）。

## 5. 回滚到 RC.1（按 digest）

1. （建议）再备份一次当前数据：`sudo sh tools/backup.sh -o /volume1/backup/nocturne ./data` + `verify-backup.sh`。
2. 停止项目 → 编辑 YAML，`image:` 改回：
   ```yaml
   image: ghcr.io/sadjdg123/nocturne:sha-2ee0983@sha256:85ee7ab40781b3d6284e52a4152f852a8b2e6f27a96e91375f296f13d2d277fa
   ```
3. 启动；`curl -s "http://$NAS_IP:8088/api/health"`（`NAS_IP` 默认 `192.168.50.141`，以 `sudo docker port nocturne` 为准）显示 `"version":"2.0.0-rc.1"`；登录检查分组 / 空间 / 图标 / 壁纸。

**一般不需要替换 `data/`**：RC.1 能直接读 RC.2 / RC.3 写过的数据（自动化测试 `test/rc1-compat.test.js` 用真实 RC.1 代码来回切换验证：会话有效、配置 / 空间 / 图标 / 壁纸完整、照常保存）。
数据里的变化与 RC.1 的处理：

| RC.2 / RC.3 写下的 | 在哪里 | RC.1 怎么处理 |
|--------------------|--------|---------------|
| 旁路字段 `fmt: 2`、`h`（指纹） | `data/spaces-guard/<账户>.json` | 不认识、忽略；RC.1 下次保存会把旁路写回旧格式（没有 `fmt`/`h`）。再升 RC.3 时启动自愈重新写成 `fmt: 2` |
| 配置历史条目的 `g: 2` 标记 | `data/config/<账户>.json` 的 `hist` | RC.1 原样复制旧 `hist` 条目，标记保留；RC.1 自己新写的条目没有 `g` |
| 顶层 `writer.v`（写入的版本号） | `data/config/<账户>.json` | RC.1 保存时写成自己的版本号，`gen: 2` 不变 |
| `NOCTURNE_COOKIE_PREFIX`（如果你在 RC.2 / RC.3 里设置过） | compose 环境变量 | RC.1 不认识，固定用 `nocturne_sid` / `nocturne_dev`：设置过前缀的话回滚后需要重新登录一次 |

回滚期间在 RC.1 里的修改，再升级到 RC.3 时原样保留（RC.3 启动时同样按当前配置重写旁路）。

**需要回到升级前的确切状态时**：停止容器，用第 1 节的备份恢复（`--force` 会把当前 `data` 改名为 `data.before-restore-<时间>` 保留，不删除任何东西），再按上面改回 RC.1 镜像启动：

```sh
cd /volume1/docker/nocturne
sudo sh tools/restore.sh --force /volume1/backup/nocturne/nocturne-backup-<升级前时间>.tar.gz ./data
```

注意：恢复备份会丢掉升级之后的所有修改；只是镜像回滚的话不需要这一步。

### 关于「回滚到 V1.1」

本文不涉及。若还要从 RC 退回 V1.1，按 `docs/v2.0-upgrade-rollback.md` 第 2 节。RC.3 起，**RC.1 写的旧格式旁路不会被用于自动找回空间**：
如果走了「RC.1 → V1.1 →（V1.1 期间空间被旧数据覆盖）→ 直接升 RC.3」这条路，RC.3 不会自动找回（日志 `spaces guard: stale … old or invalid format`），
请到 设置 → 账户 →「恢复较早的版本」手动恢复。正常的 RC.1 → RC.3 升级不受影响（启动时已按当前配置重写旁路）。

## 6. 全新安装（没有旧数据）

1. 在 NAS 上建项目目录（例如 `/volume1/docker/nocturne`）和空的 `data/`；`docker-compose.yml` 用仓库里的示例，把 `image:` 改成 RC.3 的 `标签@digest`，按需设 `PUID`/`PGID`（`id` 命令查看）。
2. Container Manager → 项目 → 新增 → 选该目录 → 构建 / 启动。
3. 打开 `http://NAS的IP:8088`（compose 的 `ports` 绑定了具体 IP 时就用那个 IP；`sudo docker port nocturne` 可查），创建管理员（密码至少 8 位）。日志：`夜曲 Nocturne v2.0.0-rc.3 已启动`、`尚未创建账户：打开网页创建管理员`。
4. 全新安装不会写 `pre-v2-snapshot-*`（没有 V1.1 数据），也没有需要自愈的旁路；第一次保存配置后 `data/spaces-guard/<账户>.json` 出现（`fmt: 2`）。
5. 用一段时间后，按第 1 节做第一次备份并校验。

## 7. 出问题时

- 容器起不来：看日志。`配置错误：NOCTURNE_COOKIE_PREFIX …` = 前缀不合法（退出码 2，不写数据）；其它情况先按第 5 节回滚镜像，数据不需要动。
- 数据不对：先试 设置 → 账户 →「恢复较早的版本」；不行再用 `restore.sh --force` 恢复第 1 节的备份。
- 任何恢复操作前，都先用 `backup.sh` 把当前状态再备份一份。
