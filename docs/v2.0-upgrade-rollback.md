# 夜曲 Nocturne · V1.1 → V2.0 升级 / 回滚 / 再升级操作手册

适用：群晖 Container Manager「项目」（docker compose）。V1.1 = `ghcr.io/sadjdg123/nocturne:sha-3e6da3c`。
V2 RC 的镜像标签与 digest 见 `docs/v2.0-rc-report.md` 第 1 节。**正式升级前请先完成 `docs/v2.0-manual-acceptance.md`。**

下文假设项目目录为 `/volume1/docker/nocturne`（里面有 `docker-compose.yml` 和 `data/`），备份目录为 `/volume1/backup/nocturne`，
夜曲仓库的 `tools/` 已复制到 NAS（例如 `/volume1/docker/nocturne/tools`）。所有命令在 SSH 里执行，需要 `sudo`。

## 为什么要用 `标签@digest`

`sha-xxxxxxx` 标签理论上不会被重新推送，但标签是可变的指针；`@sha256:<digest>` 是镜像内容本身的哈希，写上后拉到的一定是验收过的那份。
docker 同时写标签和 digest 时以 digest 为准，标签只是方便人看。

| 版本 | 镜像 |
|------|------|
| V1.1（当前在用） | `ghcr.io/sadjdg123/nocturne:sha-3e6da3c@sha256:58a4c8349242ca80ca4a46681410eafcbbb41e0411c3567e3cbef9abff19e861` |
| V2.0 RC | 见 `docs/v2.0-rc-report.md` 第 1 节 |

## 1. 升级（V1.1 → V2）

1. **备份并校验**（容器会被短暂停止再自动启动）：
   ```sh
   cd /volume1/docker/nocturne
   sudo sh tools/backup.sh --stop nocturne -o /volume1/backup/nocturne ./data
   sh tools/verify-backup.sh /volume1/backup/nocturne/nocturne-backup-<时间>.tar.gz
   ```
   看到「备份完好：N 个文件 sha256 全部一致」再继续。备份含密码哈希和会话，权限 600，请放在只有你能读的位置。
2. Container Manager → 项目 → `nocturne` → **停止**。
3. 项目 → 编辑（YAML），把 `image:` 改成 V2 RC 的 `标签@digest`（记下原来那一行，回滚要用）。
4. **构建 / 启动**（Container Manager 会按 digest 拉取）。或 SSH：`sudo docker compose pull && sudo docker compose up -d`。
5. 验证：
   - 日志有 `夜曲 Nocturne v2.0.0-rc.1 已启动`，首次启动有 `pre-v2 snapshot written pre-v2-snapshot-<时间>`；
   - `http://NAS的IP:8088/api/health` → `"ok":true`、`"version":"2.0.0-rc.1"`；
   - 浏览器登录：分组 / 项目 / 图标 / 壁纸 / 状态点正常；反向代理用户看「连接诊断」。

升级本身不改动 V1.1 的数据格式：V2 第一次写配置时只是在配置里多了 `spaces` 等字段和顶层写入标记 `writer`。
另外会多出两个目录：`data/pre-v2-snapshot-<时间>/`（固定的升级前快照，永不轮换）和 `data/spaces-guard/`（回滚写保护旁路文件）。

## 2. 回滚（V2 → V1.1）

1. 备份当前（V2）数据：`sudo sh tools/backup.sh --stop nocturne -o /volume1/backup/nocturne ./data`。
2. 停止项目；YAML 里 `image:` 改回 `ghcr.io/sadjdg123/nocturne:sha-3e6da3c@sha256:58a4c8349242ca80ca4a46681410eafcbbb41e0411c3567e3cbef9abff19e861`。
3. 启动；检查 `/api/health`（V1.1 的版本号），登录确认配置正常。

**一般不需要替换 `data/`**：V1.1 能直接读 V2 写过的配置，空间定义会原样保留（V1.1 普通编辑实测保留空间），只是 V1.1 不显示空间。
已知风险：回滚期间若在冲突面板选「用本机版覆盖」一份 V2 之前的离线版本，空间定义会被冲掉——这正是第 3 节写保护要找回的情况。

**需要回到升级前的确切状态时**（二选一，都要先停止容器）：

- 用第 1 节的备份：`sudo sh tools/restore.sh --force /volume1/backup/nocturne/nocturne-backup-<升级前时间>.tar.gz ./data`
  （`--force` 会把当前 `data` 改名为 `data.before-restore-<时间>` 保留，不删除任何东西）；
- 或用固定的升级前快照：把 `data/pre-v2-snapshot-<时间>/` 里的 `users.json`、`config/`、`icons/`、`wallpapers/` 复制回 `data/` 对应位置
  （`MANIFEST.json` 里有每个文件的 sha256，可用 `sha256sum` 核对）。快照不含会话（需要重新登录）、配置快照环和图标缓存。

## 3. 再升级（V1.1 → V2，回滚写保护）

按第 1 节同样的步骤（先备份）把镜像换回 V2。启动时以及每次读取配置时，V2 会检查：

> 配置**没有** V2 写入标记 + `data` 里**没有** `spaces` 字段 + 配置版本**比**旁路文件新 + 旁路文件里有**非空**空间

全部满足时：先把当前版本存一份 `-guard` 快照（设置 → 账户 →「恢复较早的版本」里标「自动找回空间前」），再把空间定义写回、清掉指向已删除分组 / 项目的引用，
日志记 `spaces guard: restored …`，每台设备的页面提示一次（14 天内）。V1.1 期间做的其它修改全部保留。

不会被找回的情况（设计如此）：在 V2 里明确删光空间或「恢复默认」；手动把配置换回了比旁路文件旧的版本；旁路文件被删除；数据整体换成了升级前备份。

## 4. 出问题时

- 容器起不来：看日志；先回滚镜像（第 2 节），数据不需要动。
- 数据不对：设置 → 账户 →「恢复较早的版本」先试；不行再用 `restore.sh --force` 恢复备份。
- 任何恢复操作前，都先用 `backup.sh` 把当前状态再备份一份。
