## 2. RC 阶段改了什么

- **回滚写保护**（第 8 节）：写入标记 `writer` + 旁路文件 `data/spaces-guard/<用户>.json` + 首次 V2 启动的固定快照 `data/pre-v2-snapshot-<时间>/`；再升级自动找回空间并提示一次；「恢复较早的版本」给 `-guard` 快照标「自动找回空间前」。

- **缓存**：只有 `fonts/*.woff2` 长期 immutable；`fonts.css` 改为 1 天重新校验；测试保证内容变了的脚本 / 样式 `?v=` 一定变。
- **修复**：经典外观下「设置 → 外观 → 界面」开关被 CSS 隐藏、切到经典后无法从界面切回新版（Chromium 回归发现）。
- **真实进程 + Chromium 演练脚本** `tools/e2e/`：`restore_drill.py`、`rollback_drill.py`、`rc_regression.py`、`https_proxy.py`、`rc_perf.py`（公共部分 `rc_common.py`）。

## 5. `/data` 数据清单

```
data/
├── users.json                          账户（scrypt 密码哈希）、已知设备
├── sessions.json                       登录会话
├── config/<用户>.json                   每人一份配置：{version, updatedAt, data, hist, ops, writer}；writer 是 V2 写入标记（V1.1 会丢掉它）
├── wallpapers/<用户>.jpg|png|webp       自定义壁纸（每人只保留当前一张，不进版本历史）
├── icons/<用户>/<id>.png|jpg|webp       上传的图标
├── backup/<用户>/<时间>-<序号>-v<版本>-<类型>.json   配置快照环（auto / replaced / restore / local / legacy / guard），每人 ≤30 份 / 共 ≤20MB
├── spaces-guard/<用户>.json             V2 新增：最后一次 V2 写入时的空间定义 + 版本号（回滚写保护，不参与轮换）
├── pre-v2-snapshot-<时间>/              V2 新增：首次以 V2 启动且检测到 V1.1 数据时写一次；users.json、config/、icons/、wallpapers/ + MANIFEST.json（sha256），永不轮换
└── cache/                              图标缓存（可删除，会重新下载）
```

写入一律「临时文件 → rename」原子替换；`*.tmp` 是写到一半的临时文件。

## 6. 备份 / 恢复

- 备份：`sudo sh tools/backup.sh --stop nocturne -o <备份目录> <data 目录>` → `nocturne-backup-<时间>.tar.gz`（内含 `SHA256SUMS`、`BACKUP-INFO.txt`）+ 外置 `.sha256`；权限 600；不打印文件内容。不停容器也可以（热备份：复制后逐个比对，变了重来，最多 3 次）。可选 `--exclude-ring`、`--exclude-cache`。
- 校验：`sh tools/verify-backup.sh <备份>`：归档哈希、gzip 完整性、路径安全、逐文件 sha256、无多余 / 缺失。
- 恢复：`sh tools/restore.sh [--force] <备份> <目标目录>`：先校验；目标非空则拒绝（退出码 3），`--force` 把原目录改名保留；解到旁边的临时目录、核对后一次 rename。

**演练结果（27 / 27 通过）**：V1.1 真实进程写入数据（两个账户、上传图标、壁纸、23 个项目）→ `backup.sh` → `verify-backup.sh`（7 个文件 sha256 一致）→ `restore.sh` 拒绝非空目标（退出码 3）→ 恢复到空目录 → 恢复树与原始树逐文件 sha256 相同 → V2 启动（`2.0.0-rc.1`）写出固定快照且 MANIFEST 全部一致 → 配置逐字节相同、图标与壁纸（72775 字节）相同、第二账户恢复且隔离、错误密码仍被拒绝 → Chromium 真实表单登录显示全部 23 项、图标解码、壁纸生效 → 在 V2 建空间并同步、逐个空间 DOM == 模型、无页面错误、旁路文件跟随 V2 写入。
单测另外覆盖：损坏 / 篡改 / 多余文件 / 非空目标、边写边备份。

## 7. 升级 / 回滚步骤（群晖 Container Manager，`标签@digest` 固定）

完整手册：`docs/v2.0-upgrade-rollback.md`。摘要：

**升级**
1. `sudo sh tools/backup.sh --stop nocturne -o /volume1/backup/nocturne ./data`，再 `verify-backup.sh` 校验。
2. Container Manager → 项目 → nocturne → 停止 → 编辑 YAML：
   `image: ghcr.io/sadjdg123/nocturne:sha-2ee0983@sha256:85ee7ab40781b3d6284e52a4152f852a8b2e6f27a96e91375f296f13d2d277fa`（记下原来的 V1.1 行）。
3. 启动（或 `sudo docker compose pull && sudo docker compose up -d`）。
4. 验证：日志 `v2.0.0-rc.1 已启动` 与 `pre-v2 snapshot written`；`/api/health` 版本正确；登录检查配置、图标、壁纸、状态点。

**回滚**
1. 先备份当前数据（同上）。
2. 停止 → YAML 改回 `image: ghcr.io/sadjdg123/nocturne:sha-3e6da3c@sha256:58a4c8349242ca80ca4a46681410eafcbbb41e0411c3567e3cbef9abff19e861` → 启动 → 检查 `/api/health`。
3. 一般不需要替换 `data/`；要回到升级前的确切状态，停容器后 `restore.sh --force <升级前备份> ./data`，或从 `pre-v2-snapshot-*` 复制回去。

**再升级**：同升级步骤（先备份）；回滚期间丢掉的空间会被自动找回（第 8 节）。

> 正式容器的升级要等第 12 节 Blocking 项全部完成；先按 `docs/v2.0-manual-acceptance.md` 第 6 节用**另一个端口 + 数据副本**的并行容器试用（提议，待批准）。

## 8. 回滚写保护：设计与限制

**要解决的风险（演练中实测复现）**：回滚到 V1.1 期间，V1.1 服务器不认识空间，任何不带 `spaces` 的保存（例如冲突面板「用本机版覆盖」一份 V2 之前的离线版本）都会让配置丢掉空间定义；V1.1 写配置时还会丢掉不认识的顶层字段。

**设计**
1. 写入标记：V2 每次写配置都在文档顶层写 `writer: {app:"nocturne", v, gen:2}`（不在 `data` 里，GET 不返回）。标记不见了 = 最后一次是非 V2 写的。
2. 旁路文件 `data/spaces-guard/<用户>.json`：V2 每次写配置同步记下空间定义（数组 / 明确删光的 `[]` / 没有字段 `null`）和版本号；V1.1 不读不写它，不参与快照轮换。
3. 再升级时（启动时 + 每次读取配置时），满足「无 V2 标记 + `data` 无 `spaces` + 配置版本比旁路文件新 + 旁路文件空间非空」才找回：先存 `-guard` 快照，再写回空间、清悬空引用，记日志，页面提示一次（每台设备、14 天内）。
4. 固定快照 `pre-v2-snapshot-<时间>/`：首次以 V2 启动且只有 V1.1 数据时写一次，永不轮换、不自动清理。

**限制**
- 只保护**空间定义**（含排除列表与空间外观）。V1.1 期间新增的分组 / 项目找回后只在「全部」及按分组引用的空间里出现；V1.1 期间删掉的分组 / 项目会从空间里清掉。
- 在 V2 里明确删光空间、「恢复默认」、手动换回比旁路文件旧的配置、删除了旁路文件、或整体恢复了升级前备份——都**不会**找回（设计如此，避免把用户故意的操作撤销）。
- 壁纸不进版本历史；固定快照不含会话、快照环和图标缓存（从它恢复后需要重新登录）。
- 固定快照与备份都含密码哈希，属于敏感文件。

## 9. 升级 → 回滚 → 再升级演练（19 / 19 通过）

真实进程、同端口换版本：V1.1 数据 → 升级 V2（写出固定快照）→ 在 V2「管理空间」界面建 3 个空间（日常 / 娱乐 / NAS）并同步，磁盘上有写入标记和旁路文件 → **回滚 V1.1**：V1.1 照常服务；V1.1 前端普通编辑保存后空间仍在；**实测风险**：设备 B 冲突面板「用本机版覆盖」把空间和 V2 标记一起冲掉（v4）→ **再升级 V2**：日志 `spaces guard: restored`、3 个空间名称与分组全部找回、设备 B 的覆盖内容保留（不回滚用户修改）、23 个项目一个不少、上传图标 / 壁纸 / 第二账户都在、快照环里有 `guard` 与 `replaced` 两份 → 页面提示「回滚期间被旧版覆盖掉的 3 个空间已自动找回 · 找回前的版本已存入「较早的版本」」、找回后空间切换正常、无页面错误、同一设备只提示一次 → 再重启一次：幂等（不重复找回、版本不变）。

## 10. HTTPS 反向代理（9 / 9 通过，本地模拟）

Caddy 2.10.2 + 自签名证书在本机做 TLS 反代：
- `TRUSTED_PROXY_CIDRS` 设为代理地址时：`nocturne_sid` / `nocturne_dev` 带 `Secure; HttpOnly; SameSite=Lax`；`/api/health` 报 `https=true`、`trustedPeer=true`；客户端伪造的 `X-Forwarded-For` 被 Caddy 和夜曲一起忽略。
- 对照组（不设 `TRUSTED_PROXY_CIDRS`）：转发头被忽略，`https=false`、Cookie 无 `Secure`（文档写明的默认行为）。
- 缓存头经代理不变：`/` `no-store`；脚本 `max-age=86400, must-revalidate` + gzip + ETag 304；woff2 `max-age=31536000, immutable`；`fonts.css` 1 天重新校验。
- Chromium 经 HTTPS 真实表单登录、保存并同步，无页面错误。
- 模拟部署：不改 `?v=` 时浏览器继续用旧脚本；改了 `?v=`，下次刷新即生效（index 是 `no-store`）。
- 未覆盖：真实域名证书、DSM 反代 / Lucky / cloudflared 的实际转发头行为、iOS Safari 的 Cookie 处理。

## 12. Blocking / Non-blocking

**Blocking（正式发布前必须完成；本次是 RC 试用，不阻塞并行测试部署）**
1. iPhone Safari 真机（浏览器模式 + 主屏幕模式）：真实软键盘、safe-area、长按进入编辑、手指拖动排序、底栏滑动手感。
2. Mac Safari：布局、字体渲染、快捷键、动效 / 减弱动态效果。
3. 真实群晖 NAS Docker：先备份、登录、持久化、容器重启 / 重建、LAN / WAN 访问、状态探测、在 Container Manager 里按 `标签@digest` 升级 → 回滚 → 再升级。
4. 真实 HTTPS 域名：反代转发头、`TRUSTED_PROXY_CIDRS`、Cookie `Secure`、更新后缓存刷新。

**Non-blocking（已知、可接受，后续改进）**
- 4× CPU 下手机空间切换仍有约 77 ms（中位）长任务；真机有 GPU 合成应更好，未实测。
- 手机与桌面都会下载两张内置壁纸（多约 59–273 KB）；手机壁纸分辨率低于 iPhone 物理像素。
- 字体无 preload；扩展子集 481 KB 遇生僻字才下载，弱网下首屏比经典重。
- 上传壁纸服务器不缩放（依赖前端压缩）。
- 编辑模式下手机底栏换成编辑栏，不能直接切空间（命令面板 `>` 可以）。
- 手机横屏首屏主要是时钟、搜索和切换器，分组需要下滚。
- 名称模板默认外观按空间名关键词匹配（只影响样子）。
- 回滚写保护只保护空间定义，且明确删光 / 恢复默认 / 手动换回旧配置时不找回（第 8 节）。
- 壁纸不进版本历史；固定快照不含会话。
- 所有截图与演练的服务地址是本机模拟服务（127.0.1.x），字体在 Linux 上渲染与 Apple 设备不同。
- 远端仓库经 GitHub Contents API 上传，`tools/*.sh` 在远端是 100644（本地 100755）；文档一律用 `sh tools/xxx.sh` 运行，不受影响。
- 本机完整串行 `npm test` 超过工具单次 120 秒，改为按文件并行跑；CI 跑完整串行。
